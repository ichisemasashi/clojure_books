# 定番ライブラリ観察メモ（L3 / L4 / L5）

**日付:** 2026-09-11  
**目的:** 企画約束①（定番ライブラリ入口の読解）を支える観察。実装の丸写しではなく、**マクロ境界／データ境界**を記録する。  
**環境前提:** 本書は Clojure 1.12.x。本メモは公開ドキュメントと典型的 API 形に基づく設計観察（依存追加での実行は任意）。

---

## L4 — Hiccup（HTML をマクロにしなくてよい例）

| 項目 | 観察 |
|------|------|
| 中心表現 | ベクトル／キーワードのデータ: `[:div {:class "x"} [:p "hi"]]` |
| マクロ度 | 低い。変換は主に関数（`hiccup.core/html` 等） |
| 展開を読まなくてよい理由 | DSL の見た目が「データそのもの」。評価制御や束縛の挿入が本質ではない |
| 本書への使い方 | 第11章で「マクロ HTML DSL」を作りたくなったときの対比。ケース#5 を書くなら、まず Hiccup 型（データ）で足りるか問う |
| 展開前後 | マクロ展開は主役ではない。`html` 呼び出し前後のデータ→文字列が観察対象 |

**結論:** HTML 糖衣はマクロ必須ではない。構文に見せる必要がなければデータ＋関数を選ぶ。

---

## L5 — HoneySQL（クエリをマクロにしない例）

| 項目 | 観察 |
|------|------|
| 中心表現 | マップ／ベクトルのクエリデータ: `{:select [:*] :from [:users] :where [:= :id 1]}` |
| マクロ度 | 低い。SQL 文字列化は関数（`honey.sql/format`） |
| 利点 | 合成・テスト・プログラム生成が容易。ツールがデータをそのまま扱える |
| マクロにしたくなる誘惑 | `SELECT` 風の見た目。しかし評価制御は不要で、データで十分 |
| 本書への使い方 | 第11章・ケース#6（入口のみマクロ）の「中身はデータ」理想形 |

**結論:** クエリ DSL はマクロよりデータが勝ちやすい。マクロを置くなら「読みやすさの入口」に限定する。

---

## L3 — ルーティング: Compojure vs Reitit（マクロ寄り vs データ寄り）

### Compojure（マクロ度: 中〜高）

| 項目 | 観察 |
|------|------|
| 典型形 | `(DEFROUTES app (GET "/:id" [id] ...))` のようなマクロ面 |
| 何がマクロか | ルート定義をハンドラ組立てコードへ変換する入口 |
| コスト | 展開結果・デバッグ・静的解析がデータルートより重いことが多い |
| 本書への使い方 | 「領域の語彙を構文にする」例。良い／悪いの議論材料（第11章） |

### Reitit（マクロ度: 低寄り）

| 項目 | 観察 |
|------|------|
| 典型形 | データとしてのルートツリー（ベクトル／マップ）＋関数でルータ構築 |
| 利点 | ルートをデータとして生成・検証・ドキュメント化しやすい |
| 本書への使い方 | Compojure との対比で「同じ問題域でもマクロ度を下げられる」 |

**結論:** ルーティングはマクロ必須ではない。Compojure 型は構文の魅力、Reitit 型はデータの扱いやすさ。約束①では「両方の入口を展開またはデータ形で説明できる」ことを目指す。
