## 14.1 動機

マクロを増やすほど、読む人・ツール・オンボーディングのコストが上がる。  
通読版の締めは、**書く前と書いた後のチェックリスト**である。

## 14.2 書く前

1. 評価順・短絡が本質か？  
2. 新しい構文／束縛が必要か？  
3. データ＋関数では足りないか？  
4. 呼び出し側にマクロ感染を強いないか？  

一つでも「いいえ」なら、まず関数またはデータ API を設計する。

## 14.3 書いた後

1. 変数捕獲はないか？（`gensym` / `x#`）  
2. 二重評価はないか？（`let` で一度）  
3. 展開結果は読めるか？  
4. 展開テストはあるか？  
5. 失敗時のメッセージは分かるか？  

## 14.4 よくある失敗（短く）

| 失敗 | 症状 |
|------|------|
| マクロ感染 | 使う側もマクロや特殊な呼び出しを強いられる |
| 第一級扱い | マクロを値として `map` しようとして詰まる |
| データで足りるもののマクロ化 | HTML／SQL／ルートを全部構文にしてしまう |

対比の観察は [`notes/ライブラリ観察_L3_L4_L5.md`](../notes/ライブラリ観察_L3_L4_L5.md)（Hiccup / HoneySQL / ルーティング）。

## 14.5 演習（判断）

実務でありがちな次の案を、チェックリストで判定せよ（各2–3行）。

1. 社内の `defroute` マクロ  
2. 設定マップを生成するだけの `defconfig` マクロ  
3. テスト用に式の実行時間を測るマクロ  
4. レコードのアクセサを一括生成するマクロ  
5. `if` の糖衣をチーム独自に増やすマクロ  

## 14.6 まとめ — 本書の約束の再確認

- **読む** … 展開を見る  
- **書く** … 衛生を守る  
- **控える** … 関数とデータの境界を先に決める
