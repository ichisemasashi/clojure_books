## 2. なぜマクロが必要か（動機）

マクロが解く問題を先に示す。

1. **評価の制御** — 引数をすぐ評価せず、条件・遅延・短絡を表現したい
2. **構文の拡張** — 言語にない制御構造・束縛形式を追加したい
3. **繰り返しの抽象化（コンパイル時）** — 実行時関数では表現しにくい定型コードを生成したい
4. **ドメイン言語（DSL）** — 問題領域に近い見た目のコードを、通常の Clojure に変換したい
5. **パフォーマンス／ゼロコスト抽象** — 実行時ディスパッチを避け、展開結果を最適化したい（慎重に）

対比として必ず書くこと:

- **関数で足りるとき** → マクロにしない
- **マクロが必要なとき** → 評価順・構文・束縛・コード形状が本質

## 3. 記述すべき機能・概念（カリキュラム骨格）

### Part A — 評価とコード・アズ・データ

マクロ理解の土台。ここが弱いと以降がすべて曖昧になる。

| トピック | 記述すべき内容 | 学習者ができるようになること |
|----------|----------------|------------------------------|
| 読み込み・評価の段階 | read → macroexpand → compile/eval の流れ | 「いつ」コードが形を変えるかを説明できる |
| フォームとデータ | リスト・シンボル・メタデータが「コード」であること | コードをデータとして操作する感覚を持つ |
| 特殊形式 vs マクロ vs 関数 | 評価規則の違い、拡張点の違い | エラーや挙動の原因を分類できる |
| クォート族 | `quote` / `'` | 評価を止めてフォームを値として扱える |
| Syntax-quote | `` ` ``、名前空間修飾、`` `foo# `` の自動 gensym | 展開結果のシンボル衝突を避けられる |
| Unquote / splicing | `~` / `~@` | テンプレート内に計算結果や列を埋め込める |
| `eval` との違い | 実行時評価とマクロ展開の違い、いつ使う／使わないか | マクロと `eval` を混同しない |

### Part B — マクロの定義と展開

言語機能としてのマクロ API。

| トピック | 記述すべき内容 | 学習者ができるようになること |
|----------|----------------|------------------------------|
| `defmacro` | 引数は未評価のフォーム、戻り値は展開後フォーム | 最小のマクロを定義・呼び出しできる |
| マクロ展開の確認 | `macroexpand` / `macroexpand-1` / `macroexpand-all`（`clojure.walk`） | 自分のマクロの出力を検証できる |
| `&form` / `&env` | 呼び出し元フォーム、局所環境（高度だが早めに存在を示す） | デバッグ・高度なマクロの入口を知る |
| 多重アリティ・可変長引数 | マクロでも通常の仮引数パターンが使える | 実用的な API 形状を設計できる |
| ドキュメントとメタデータ | `:doc`、arglists、マクロであることの表示 | ライブラリ品質のマクロを書ける |
| マクロの配置とロード順 | 名前空間、`require` の `:refer`、コンパイル順序 | 「未定義マクロ」系のエラーを避けられる |

### Part C — 健全性・衛生・よくある罠

教科書として必ず独立させるパート。

| トピック | 記述すべき内容 | 学習者ができるようになること |
|----------|----------------|------------------------------|
| 変数捕獲（capture） | 意図しない束縛の取り込み | バグの典型パターンを認識できる |
| 意図的キャプチャ | anaphoric macro（賛否含む） | 意図とリスクを説明したうえで使える／避ける判断ができる |
| Gensym | `gensym`、`` x# `` | 衛生的な局所束縛を生成できる |
| 二重評価 | 展開結果で同じ式が複数回評価される問題 | `let` で一度束縛する定石を使える |
| マクロ衛生の限界 | Clojure のマクロはデフォルトで衛生的ではない（CL と同様。Scheme の hygienic とは違う） | 「自分で衛生を守る」姿勢を持つ |
| エラーメッセージ設計 | 展開時の `assert` / 例外、良い失敗の仕方 | 利用者に分かりやすいマクロを書ける |
| デバッグ手法 | 展開結果の印刷、段階的展開、小さな例から | 壊れたマクロを自己修復できる |

### Part D — 制御構文・束縛の拡張（マクロで「できること」の中核）

標準ライブラリや定番パターンを「機能カタログ」として書く。

| できること | 代表例・題材 | 要点 |
|------------|--------------|------|
| 条件・分岐の再表現 | `when` / `when-not` / `if-not` / `cond` 系 | 真偽と副作用の組み合わせ |
| 短絡・逐次 | `and` / `or` / `when-let` / `if-let` | 評価を止める・束縛と条件を同時に |
| 繰り返し・走査風構文 | `doseq` / `dotimes` / `for`（理解用） | マクロが生成するループの形 |
| リソース管理 | `with-open` / `with-redefs` | 開始・終了の保証を構文にする |
| 例外・制御 | `try` 周辺の糖衣、早期 return 風 API の是非 | 例外マクロの設計判断 |
| 遅延・非同期の糖衣 | `delay`、簡易 `future` 風、チャネル DSL への橋渡し | 「構文」と「実行モデル」の分離 |
| 局所束縛の拡張 | `let` 風 DSL、複数値束縛、ネスト平坦化 | 束縛マクロの定石 |
| 定義マクロ | `defn` / `defmacro` 自体、`defonce`、レコード定義糖衣 | 「定義する定義」 |

### Part E — コード生成パターン

マクロ実装のレシピ集。

| パターン | 内容 | 用途 |
|----------|------|------|
| テンプレート展開 | syntax-quote 中心の素直な展開 | ほとんどの糖衣構文 |
| ヘルパー関数への委譲 | マクロは薄く、複雑な変換は関数に | テスト容易性・可読性 |
| 再帰的展開 / 複数パス | 大きな DSL を段階的に通常コードへ | 中〜大規模 DSL |
| シンボル・キーワード駆動 | オプションマップやフラグで分岐する API | 設定的マクロ |
| コード行走査 | `clojure.walk`、手動の木変換 | リライト・最適化・解析 |
| マクロがマクロを生成 | マクロ工場 | ボイラープレート削減（複雑度に注意） |
| コンパイル時計算 | 展開時に定数畳み込み・表生成 | 性能・組込みデータ |

### Part F — DSL 設計

「マクロで何が得意か」を設計論としてまとめる。

| トピック | 記述すべき内容 |
|----------|----------------|
| 内部 DSL の種類 | 埋め込み式（Clojure に近い）vs 外見が大きく違う DSL |
| API 境界 | マクロ面と関数面の切り分け（マクロは入口だけ、中はデータ） |
| データ駆動との比較 | マップ／ベクトルで表現できるならマクロ不要、という判断基準 |
| 読みやすさのトレードオフ | 書く側の短さ vs 読む側・ツール・エラーのコスト |
| 良い DSL の例の読み解き | 例: `core.async` の `go`、`compojure`、`honeysql`（データ寄り）との対比 |
| 悪い DSL の兆候 | 魔法が多すぎる、展開結果が読めない、関数で十分なもの |

### Part G — エコシステム・実践

| トピック | 記述すべき内容 |
|----------|----------------|
| 標準マクロの読み方 | `clojure.core` の短いマクロをソースで追う演習 |
| 仕様・テスト | マクロの単体テスト（展開結果比較）、`clojure.spec` との関係 |
| 型・静的解析との関係 | マクロがツールに与える影響（IDE、clj-kondo 等）の概要 |
| CLJS / `.cljc` | リーダー条件、マクロの置き場所（`*.clj` / `macros` 名前空間）の基礎 |
| いつマクロを避けるか | チェックリスト（最終章の要約） |

## 4. 「マクロでできること」一覧（機能マップ）

学習者向けに、能力を一文で列挙する。詳細は各 Part で展開する。

### 4.1 言語を広げる

1. 新しい制御構造を追加する（条件・ループ・早期脱出風 API）
2. 新しい束縛形式を追加する（`if-let`、カスタム `let`）
3. 定義構文を追加する（独自の `def` 系、レコード／プロトコル糖衣）
4. 呼び出し構文を領域向けに変える（ルーティング、クエリ、UI、状態機械）

### 4.2 評価を支配する

5. 引数の評価を遅らせる・条件付きにする
6. 同じ入力フォームを、文脈に応じて別のコードに変換する
7. 展開時に計算し、実行時コストを減らす（定数・表・コード生成）

### 4.3 繰り返しと一貫性

8. ボイラープレートを一箇所の定義から生成する
9. 複数の類似定義（関数群・定数・変換）をデータから一括生成する
10. ログ・計測・認可などの横断的関心を構文レベルで挿入する（AOP 的利用。乱用注意）

### 4.4 抽象の層を作る

11. 薄い糖衣（thin wrapper macro）で API を読みやすくする
12. 厚い DSL で、問題領域の語彙をそのまま書く
13. 「見た目は DSL、実体はデータ＋関数」へ橋渡しする入口だけをマクロにする

### 4.5 できないこと・向いていないこと（明示する）

14. **実行時に初めて決まる値**だけで分岐する「動的マクロ」は通常の設計ではない（関数・マルチメソッド・データで行う）
15. **第一級の値としてマクロを渡す**ことはできない（関数とは違う）
16. **単純な変換や計算の抽象**には関数／データが適する
17. **過度に賢いマクロ**は、ツール支援・オンボーディング・デバッグを壊しやすい

## 7. 記述の方針（執筆ルール）

1. **必ず展開前後を併記する** — 見た目の糖衣だけで終わらせない
2. **同じ問題を「関数版」と「マクロ版」で対比する** — 必要性を体感させる
3. **`clojure.core` の実在マクロを読む演習を毎 Part に入れる**
4. **「書いてはいけない」例を先に見せ、直す** — 罠を知識として固定する
5. **用語は日本語＋英語記号を併記**（例: 変数捕獲 / variable capture）
6. **CLJS 差分は「基礎の後の補章」**にし、JVM Clojure を主軸にする

## 9. 一言まとめ

Clojure マクロの教科書が扱うべき中心は、「構文と評価順をコンパイル時に変換する力」と「その力を安全に制限する判断」である。機能としてはクォート／`defmacro`／展開／衛生／標準パターン／DSL 設計を順に積み上げ、できることとしては制御構文・束縛・定義・コード生成・領域言語を、関数・データとの境界を常に明示しながら記述する。
